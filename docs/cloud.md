# Local-to-Azure migration

## Already implemented

- Stateless FastAPI API; the browser sends at most six prior question/plan pairs. There are no server-side chat sessions to coordinate.
- Container packaging with React served at the same origin, a non-root process, and process health check.
- Configuration from environment, server-only keys, OpenRouter default plus direct OpenAI and Azure OpenAI v1 adapters.
- Optional `DefaultAzureCredential` for Azure OpenAI and PostgreSQL. PostgreSQL acquires a new token for each physical connection, so pool recycling does not reuse an expired startup token.
- Connection and request bounds, parameterized SQL, transaction-local read-only and timeouts, exact decimal JSON strings, stage timings, request IDs, audit events.
- Optional Azure Monitor OpenTelemetry exporter through `APPLICATIONINSIGHTS_CONNECTION_STRING` and the `azure` dependency extra. Database SQL instrumentation is disabled; do not enable content/prompt capture for sensitive workloads.

## Deployment sequence (not yet provisioned)

1. Build/test the Docker image and push it to Azure Container Registry. Deploy the image to **Azure Container Apps**, port 8000. Start with **one process per replica**, pool size 4, minimum replica 1 for predictable interactive latency and a small maximum replica count. Estimate total DB connections as `replicas × workers × DB_POOL_MAX_SIZE` and leave room for KNIME/admin connections. Scaling to zero reduces idle cost but introduces cold starts.
2. Enable **Container Apps built-in authentication**, Microsoft Entra provider, correct tenant, require authentication, and reject unauthenticated requests. Configure allowed users/app roles at the identity boundary. The API trusts `x-ms-client-principal-id` only in `AUTH_MODE=azure_container_apps`. Do not put that mode on a public bare server: externally supplied headers are not identity proof. ACA must remove user-supplied identity headers and be the only ingress path. Test authenticated and unauthenticated requests before exposure. The application is single-workspace; tenant/row authorization is future work.
3. Set `APP_ENV=production`, `AUTH_MODE=azure_container_apps`, exact `ALLOWED_HOSTS` (include localhost for the health check), `PGSSLMODE=verify-full` and a trusted CA root configuration. Same-origin static hosting needs no public CORS origins. Enable HTTPS-only ingress.
4. Use a separate read-only database identity. Apply `sql/04_agent_reader_role.sql` in the personal database only, grant it to the new login/Entra principal, audit memberships and inherited PUBLIC privileges, set `default_transaction_read_only=on`, and verify write denial using an isolated test. Keep KNIME’s load identity separate. Prefer private network access from the container environment to PostgreSQL.
5. For Azure models, provision a **GPT-4.1 nano** deployment in a supported region, set `OPENAI_PROVIDER=azure`, `AZURE_OPENAI_ENDPOINT=https://RESOURCE.openai.azure.com`, and `OPENAI_MODEL=DEPLOYMENT_NAME`. Leave `AZURE_OPENAI_API_KEY` empty to use managed identity; grant the identity appropriate inference RBAC. Do not append `/openai/v1` to the endpoint setting; the adapter adds it. Keeping OpenRouter is supported with `OPENAI_PROVIDER=openrouter`, `OPENAI_MODEL=openai/gpt-4.1-nano`, and `OPENROUTER_API_KEY` supplied through an ACA **Key Vault secret reference**. Direct OpenAI uses provider `openai`, model `gpt-4.1-nano`, and `OPEN_AI_API_KEY`. OpenRouter routing may use Azure as an upstream provider, but that does not imply your own Azure tenant, region, managed identity, or network boundary. Use direct Azure if those controls are required.
6. For Entra PostgreSQL auth, provision the identity as a database principal through the server’s Entra administrator, grant only the reader role, set `PG_AUTH_MODE=entra` and `PGUSER` to that principal’s database role. The adapter uses the `ossrdbms-aad.database.windows.net` token scope. A token is authentication, not a grant of database permissions.
7. Confirm built-in **PgBouncer** support and `pgbouncer.enabled` on your server/tier before changing `PGPORT` from 5432 to 6432. Test transaction pooling. The app disables named prepared statements and uses transaction-local settings; it does not rely on session-level state.
8. Enable **Query Store**, inspect **Query Performance Insight**, and review **autonomous tuning** recommendations after real traffic. Configure diagnostics/retention and monitor capture overhead. Do not blindly apply every suggested index or force index scans. Refresh PostgreSQL statistics after successful KNIME reloads in an approved maintenance step.
9. Send application/audit stdout to Azure logs, configure Application Insights and alerts (errors, rate limits, model tokens, planning latency, query latency, pool saturation). The local Markdown sink needs a writable mounted path. With multiple replicas, use separate per-replica files or replace the local file sink with centralized append-only audit storage; a shared Markdown file is not a distributed audit system. Retain restricted access and retention policies.
10. Add per-user quotas at **API Management** or another authenticated ingress, budget alerts, broader evaluation cases and load tests. The current per-process semaphore is only overload protection. Use Foundry evaluation/monitoring when the Azure model route is active; reassess content filtering and prompt injection coverage before public deployment.

## PostgreSQL performance and retrieval priorities

1. Measure separately: metadata, model planning, DB time, end-to-end time, and p50/p95 at realistic concurrency. A connection pool or SQL index cannot eliminate model/network latency.
2. Keep selective predicates on the indexed fact FK (`date_key`) and joins on dimension primary keys. Already implemented. Existing category/date/customer/seller/status indexes remain unchanged. The optimizer may correctly choose a sequential scan for broad aggregates.
3. Use Query Store and `EXPLAIN (ANALYZE, BUFFERS)` on reviewed read-only queries to find the next bottleneck. EXPLAIN ANALYZE executes its query and incurs read load; the verification script uses only a fixed SELECT and the same timeout/audit path.
4. If large repeated monthly/category aggregates dominate, consider PostgreSQL materialized views with KNIME-orchestrated refresh after a successful warehouse load. `REFRESH ... CONCURRENTLY` needs an appropriate unique index and has refresh cost. Do not add per-category distinct orders to compute an overall order count: distinct counts are not additive.
5. At current catalog size, avoid embeddings. At larger schema/glossary size, use PostgreSQL full text search (`tsvector`, `websearch_to_tsquery`, GIN) first. For semantic schema/example retrieval, evaluate `pgvector` HNSW or Azure `pg_diskann`, measure recall/latency, and keep exact SQL aggregates for facts. Embeddings retrieve relevant descriptions; they do not accurately sum revenue.
6. Azure AI Search is an alternative for a future document corpus spanning stores. Azure `azure_ai` operators are candidates for offline text enrichment. Neither is required for the present seven-table relational analytics contract. No extension is installed by the application.
7. Read replicas can separate analytical reads from ETL at larger scale; evaluate replication lag, reload visibility and cost. Result caching would need identity scope, semantic version and an explicit KNIME load/version key.

## Known limits

This is an aggregate analytics agent, not an autonomous SQL administrator or a universal BI semantic engine. Strict schemas guarantee output shape, not semantic correctness. A model can choose the wrong allowed metric/filter. Users see SQL and definitions to inspect that choice; regression evaluations must expand with actual usage. The included live suite is a smoke test, not an accuracy benchmark. The app does not implement multi-tenant authorization, durable chat history, a distributed quota service, infrastructure-as-code, or disaster recovery automation. Azure migration adapters and container packaging must be validated in the target tenant before production use.
