# Agent engineering decisions

Research date: 2026-09-22. Scope: local first, existing Azure PostgreSQL warehouse, React, FastAPI, GPT-4.1 nano. The user clarified that their credential is an OpenRouter key; the final default uses `OPENROUTER_API_KEY` and model `openai/gpt-4.1-nano`. “Supported” means implemented in the app; “deferred” means researched and documented, not provisioned or enabled on Azure. No new Azure resources, extensions, tables, or server settings were created for this build.

| What we wanted to do | Options considered / Azure built-in check | What we did | Why | How to scale later | Tradeoff | Weakness of chosen option |
|---|---|---|---|---|---|---|
| Turn questions into analytics | Free-form text-to-SQL; strict structured plans; Azure `azure_ai.generate()` semantic operators [1][2][3] | GPT-4.1 nano generates a typed plan; a deterministic compiler owns SQL | Keeps one model call and makes metric definitions and execution scope reviewable | Add reviewed dimensions/metrics and evaluation cases; retain compiler boundary | Less expressive than arbitrary SQL | Unsupported analyses require code changes; a valid plan can still misunderstand intent |
| Use the requested model locally | OpenRouter; direct OpenAI; Azure OpenAI deployment with v1 API [1][2][20] | OpenRouter is default, model `openai/gpt-4.1-nano`; direct OpenAI and Azure v1 remain configurable | User has an OpenRouter credential; preserve the requested model and use the correct endpoint | Set provider, Azure endpoint and deployment name; use managed identity | OpenRouter adds another processor and network hop; requests require schema-supporting endpoints and `data_collection=deny` | Provider routing/account policy affect availability and latency; this is not an Azure-only data boundary |
| Keep computations correct and latency low | Second LLM summary; database aggregate plus deterministic rendering | PostgreSQL performs aggregation; backend formats the result and sends no result rows to the model | One model call, exact monetary strings, no invented numeric narrative | Extend deterministic analytical summaries with tests | Less conversational output | Does not explain causal reasons, forecast, or compute arbitrary derived metrics |
| Reuse connections | New connection per request; driver pool; Azure built-in PgBouncer [4] | Small bounded Psycopg pool; prepared statements disabled; transaction-local settings | Avoid repeated handshakes; remain compatible with transaction pooling | Verify built-in PgBouncer availability/configuration, then use port 6432; budget replicas × workers × pool size | One pool per process | Local pooling does not enforce a global connection limit across replicas |
| Optimize warehouse queries | Extra indexes, custom optimizer, Azure Query Store/Query Performance Insight/autonomous tuning [5][6] | Reuse existing FK indexes; push YYYYMMDD filters onto indexed fact key; join only required dimensions; ship read-only EXPLAIN verification | Avoid speculative indexes and extra ETL write costs | Capture a representative workload in Query Store, review autonomous tuning recommendations, benchmark indexes | No promise that all queries use indexes; small scans may be faster | Broad aggregates still scan matching fact rows; adding LIMIT bounds output, not all computation |
| Retrieve the right schema and terms | Full schema every turn; vector RAG; native PostgreSQL full text search; `pgvector`/DiskANN; Azure AI Search [7][8][9] | Reviewed semantic catalog plus a 60-second cache of at most 200 category labels | Seven tables and ~74 categories are small; vector search adds cost and failure paths without useful benefit here | First use PostgreSQL `tsvector` + GIN for a large glossary; add pgvector or managed DiskANN for semantic schema/example retrieval; evaluate Azure AI Search for cross-source documents | Complete small-catalog context rather than approximate retrieval | Fixed catalog needs maintenance and does not scale unchanged to thousands of tables |
| Use Azure in-database AI appropriately | `azure_ai.generate`, `extract`, `is_true`, `rank` semantic operators (documented Preview) [3] | Evaluated and deferred; no LLM inside SQL execution | User's credential is for OpenRouter, not a provisioned Azure model endpoint; aggregation needs SQL, not semantic inference per row | Consider enrichment/reranking through controlled ETL when unstructured data enters the warehouse | Does not use every available Azure AI feature | Preview availability and per-row latency/cost would need new measurements; no automatic ETL enrichment |
| Speed up repeated questions | Per-user result cache; Azure Managed Redis; PostgreSQL materialized views [10][11] | Cache metadata only; query results stay fresh | Warehouse is small and KNIME can refresh it; avoids stale metrics and cross-user cache leakage | For measured expensive aggregates, refresh materialized views after successful KNIME loads; use Redis only when cross-replica caching justifies it | Every question still runs aggregate SQL and a model plan | Warm questions are not instantaneous; future caches must include auth scope, plan version and load version |
| Bound workload and retries | Unbounded agent loop; queue; API Management limits; Container Apps scaling [12][13] | One plan per question, one provider retry, max 4 concurrent requests by default, query/lock timeouts, result cap, 32 KiB request cap | Predictable local resource usage; returns 429 under saturation | APIM for per-user quotas and tenant budgets; ACA replica limits; queue only for long jobs | Local limit is per process, not per user | A public service needs identity-aware distributed quotas and spend alerts |
| Protect the warehouse | Prompt-only instructions; regex SQL validation; restricted plans; PostgreSQL roles and read-only transactions [14] | Strict enums + parameterized SQL + read-only transactions; sandbox DB name enforced; optional reader grant script | Model cannot choose functions/tables or emit executable DDL; no database mutations in the app | Dedicated Entra database identity with only SELECT; RLS or scoped views if tenant data is introduced | Existing local credentials remain usable | Administrative credentials are broader than required; read-only transactions are not a replacement for least privilege |
| Authenticate people and services | Custom auth; Azure Container Apps built-in auth; managed identity; Key Vault [15][16][17] | Loopback local mode; cloud mode requires ACA identity header; managed-identity adapters for Azure OpenAI/PostgreSQL | Reuse Azure auth infrastructure and token rotation | Require Entra sign-in at ACA ingress, restrict allowed tenant/users, private PostgreSQL network, Key Vault secret references | Cloud auth depends on trusted ingress configuration | Header check is safe only behind ACA’s authenticated, non-bypassable ingress; multi-tenant authorization not implemented |
| Observe quality, cost and latency | Custom dashboard; Azure Monitor OpenTelemetry/Application Insights; Foundry evaluations [18][19] | Request IDs, separate model/DB timings, token usage in responses, redacted audit, optional Azure Monitor exporter, live regression suite | Makes failures traceable and tests intent mapping separately from execution safety | Export to Application Insights; expand Foundry evaluations and capture latency/error/budget alerts | Local metrics are lightweight and file logs are single-process | No production dashboards or broad quality guarantee; cloud audit needs managed retention and access control |
| Package for local and cloud | Two services; static site + API; one container; Kubernetes [12] | React/Vite + FastAPI, one multi-stage non-root container serving both, locked dependencies, CI | Same origin simplifies deployment; no orchestrator needed locally | Deploy image to ACA and ACR; split frontend to Static Web Apps when caching/distribution needs justify it | Frontend/backend initially scale together | No IaC or deployed environment is claimed; cold starts and shared scaling remain |

They are design choices, not an Azure compliance certification or a claim that every cloud feature is already enabled.
